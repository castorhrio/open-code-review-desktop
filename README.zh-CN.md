# Open Code Review 桌面版

[`alibaba/open-code-review`](https://github.com/alibaba/open-code-review)（`ocr`）的**非官方 Windows 桌面界面**。`ocr` 是阿里巴巴开源的 AI 代码审查 CLI，45k+ star。

审查引擎是**未经修改的官方 `ocr` 二进制**。本项目只做封装：拼命令行、流式读进度、解析 JSON，并把范围确认、成本控制、问题分级、历史续跑做成图形界面。这里不重新实现任何审查逻辑。

开发、打包、安装的完整细节见 [`使用说明.md`](使用说明.md)。

## 版本状态

`v0.1.13`（最新）——对照 `ocr v1.13.3` 验证。

已用真实 CLI、零 token 成本端到端验证：

- 四种审查范围，以及工作区 / 分支对比 / 单提交 / 全量扫描的 `--preview`
- 按模式的参数白名单（`ocr scan` 会拒绝 `--effort`、`--no-filter`、`--background-file`，误传会让整单直接失败）
- 多服务商并存配置、「设为当前」，以及按次覆盖（`--provider` / `--model` 只出现在那一次命令行里，不写回全局配置）
- 按表单值测试连通（跑在隔离的空 HOME 里，不写配置）、失败时报错里的模型名可一键回填、保存后自动复测
- 失败输出处理、会话列表 / 载入 / 导出 HTML / 删除、`ocr rules check`、`ocr llm providers` 解析
- 安装版能启动并调用到内置二进制
- 运行日志实时转发 CLI 自己的进度行（`full-scan: N file(s) discovered`、`estimated cost: …`、`scan dispatch: …`、`Session: …`、逐个文件的排除与失败原因），同时不把失败载荷刷进日志
- 一次真实的全量扫描已跑通并产出评论（1 个文件、4 条意见、103K token、3m36s），结果页按该载荷渲染
- 两个结果界面在千级规模下的表现：`?huge=1` 挂载 1200 条评论——结果列表每一行、阅读页每一块——405ms 完成，并有 8s 上限断言；两者都不做虚拟化，这个决定有测量依据
- 125% 与 150% 系统缩放下的渲染：视觉审计把八个布局最紧的 shot 以两种 deviceScaleFactor 各重跑一遍，两档全绿
- 运行中的实时进度（发现文件数、已完成工具调用、已产出评论、CLI 自己的成本预估行）；工具调用流水只计数不刷屏；大规模扫描前有规模与成本二次确认
- `ocr llm test` 已在真实服务商上通过（含 tool-call 往返）
- 达到上限的运行不算干净：读取 CLI 的 `review_limit_reached` 警告（上游 v1.13.1 新增）与 `summary.budget_exceeded`，所以「撞到上限且零发现」的运行会说明情况，而不是断言代码没问题——两个结果界面都如此
- 上限证据不会随关窗消失：刚跑完一个撞上限的运行就关掉应用，退出前会先把待写入的证据落盘，重开的会话不会又变回「干净」——这一条在真实 Electron 进程里验过，不是推理出来的
- 起不来的运行只报一次：进程起不来时 Node 会同时发 error 与 close 两个事件，此前同一次失败会被报两遍——两条 toast、两条日志
- 失败的运行会在报告正文里说清原因：CLI 自己的 `manifest.run_failure` 分类会被译成中文（超时、配置不对、预算用尽——每种该做的事不同），并写进报告正文、挨着评论，所以转发出去的那份文档会说明它为什么不是全量审查；CLI 自己的原始原因引在下面，并标明是 CLI 的话

**已验证（2026-10-13）**：一次真实全量扫描（12 个文件、8 条意见、173K token、1m41s）产出了分节的 `project_summary`，要点带按真实文本渲染、按上限截断并带渐隐。是否产出由 CLI 决定：同一仓库一次 2 条评论的工作区运行就没有产出，所以"何种运行会产出"是上游行为、不是本项目的承诺；会话也依旧不持久化它，因此旧会话不显示要点带是正确行为，不是缺渲染。真实审查产出的评论本身早已验证过：一次完成的扫描留下的 4 条意见，从会话载入后正常显示在结果列表里。

## 为什么需要图形界面

CLI 很强，但一切都发生在终端里：读几十条行级意见、区分"审完了"和"被预算截断了"、续跑一次中断的审查，都要靠人记住 flag 和 session id。这里把这些变成看得见、且不容易做错的操作。

## 主要能力

| | |
| --- | --- |
| **四种范围** | 工作区改动 · 分支对比（merge-base）· 单个提交 · 全量扫描 |
| **先预览再花钱** | 列出将进入审查的文件，并说明每个被排除文件的原因（二进制、凭据路径、暂不支持类型等），不消耗 token |
| **成本护栏** | `--max-tokens-budget` 与 `--timeout` 是真实输入项而不是藏起来的 flag；规模大到会花钱的扫描，启动前先拿它们对一遍账 |
| **诚实的运行状态** | 完成 / 部分完成 / 失败 / 有警告 徽章，并列出**没有审完**的文件与原因——被截断的运行绝不会显示成"干净通过" |
| **续跑** | 中断、取消或部分失败的运行可基于官方会话续跑，已审过的文件不重复计费；分支对比 / 单个提交 / 全量扫描适用，工作区改动的会话只留档、CLI 不支持续跑，界面也就不会给一个注定失败的按钮 |
| **会话历史** | 查看、载入、续跑、导出离线 HTML 报告、删除 |
| **代码定位准确** | 审查目标是某个 ref 时，代码面板用 `git show` 读取该 ref 下的内容（`HEAD` 也一样），而不是你的工作副本；文件不在那个 ref 里时，面板会明说，并让你自己选择是否去看工作区的版本 |
| **钉在被审查的那一版** | CLI 在开跑前就把分支/提交解析成具体的 commit 并记进清单，所以代码面板、表头和报告读的都是**当时那个 commit**；分支后来又前进过，重开历史会话看到的仍是被审查的那一版，而不是分支「现在」的内容 |
| **筛选与操作** | 严重级 / 类别 / 关键词筛选，`↑` `↓` 或 `j` `k` 切换，复制建议代码，导出 JSON |
| **通读整份审查** | 一键把一次运行排成一份文档：按文件分组、有最严重问题的文件排在最前、CLI 写的 Markdown 正常渲染——结果页是一条一条看的，阅读页才是拿来读和搜的 |
| **看得见它在跑** | 把 CLI 每一次工具调用实时列在屏幕上（读哪个文件、查了什么、耗时多久），因为三分钟沉默和「程序卡死了」看起来是一回事 |
| **首次引导** | 三步引导、输入分支时实时校验，并把 CLI 的英文报错翻译成可行动的中文提示 |
| **多服务商与按次切换** | 配置里可同时保留多个服务，「设为当前」决定默认用哪个；审查页还能只为这一次运行换服务或模型（等同 `--provider` / `--model`），换完不改全局配置 |
| **不保存也能测** | 「测试连通」直接按你填写的值试（不写任何配置），保存之后会自动再测一次；服务商拒绝模型名时，它认的名字会变成可点的按钮，点一下就填进模型框 |
| **应用内更新** | 安装版启动后检查已发布的版本、后台下载、校验 SHA-512，你说一声就重启完成更新——不用再回浏览器手动找 |
| **Key 不出本机** | 配置只通过 `ocr config set` 写入官方 `~/.opencodereview/config.json`，本程序不另存副本，也只连接你配置的端点 |

## 安装

**方式 A — 安装包（推荐）。** 从 [Releases](../../releases) 下载对应版本的 `*-setup.exe` 双击安装。当前用户级安装，不需要管理员权限。因为**未做代码签名**，SmartScreen 可能提示"Windows 已保护你的电脑"→ 点「更多信息」→「仍要运行」。

**方式 B — 免安装绿色版。** 直接运行 `*-portable.exe`，无需安装。

> v0.1.0 的资产已在本项目由 `ocr-desktop` 改名后原地重命名为 `open-code-review-desktop-0.1.0-*.exe`；文件字节未变（SHA-256 已核对），但改名前的下载链接现在会返回 404。

**方式 C — 源码运行。**

```bash
npm install      # 会下载原生 ocr 二进制（约 55 MB）
npm run dev      # Vite 热更新 + Electron
npm start        # 构建界面后运行
npm run dist     # 打 Windows 安装包到 release/
```

## 第一次使用

1. 顶部选择仓库目录（必须是 git 仓库根目录，且 `PATH` 上有 Git ≥ 2.41）。
2. 「设置」里选择模型服务、填 API Key 与模型名 → **测试连通**（按你填写的值直接测，不用先保存）→ 满意后点 **保存并设为当前**（保存后会自动再测一次）。已配置多个服务时，列表里的「设为当前」决定默认使用哪个，审查页的「本次使用的服务」只为单次运行换。
3. 回「审查」页。文件清单会自己算好（预览不花 token），先看清这个范围到底要审多少个文件，再点页面底部常驻的 **开始审查**。其余调参项（档位、并发、单次换服务、token 上限、排除规则…）都收在「调整这次审查的参数」里，全部有可用默认值。

## 代码结构

```
src/                     React 19 + TypeScript + Tailwind v4 + Radix UI（Vite 构建到 out/）
main.js                  Electron 主进程、IPC、窗口状态
ocr-service.js           封装契约：按模式的 flag 白名单、输出解析、会话
git-service.js           仓库信息、ref 解析、读取指定 ref 下的文件
preload.js               contextBridge 接口
```

动构建配置前要知道的两点：

- **`asar` 必须保持 `false`。** 开启后 `resolveNativeBinary()` 返回 `app.asar\…` 路径，`fs.existsSync()` 会返回 true 骗过检查（Electron 只给 `fs` 打了补丁），而 `spawn()` 走 CreateProcess 不认识该路径直接 ENOENT——每次审查静默失败。
- 界面产物目录是 **`out/`**（不是 `dist/`），且以 `base: './'` 构建，才能在 `file://` 下加载。

## 发版

`node tools/release.mjs <x.y.z>` 会升版本、提交 `chore(release): <x.y.z>`、跑完整门禁、打 Windows 安装包，并对 `release/` 重跑密钥扫描；若 electron-builder 撞上 `win-unpacked.tmp` 被锁的重命名失败，它会自动改到新输出目录构建，再把产物移回 `release/`。它停在两件属于人的动作之前：推送提交，以及发布 GitHub Release（自动更新源读的是 releases/latest）。

## 已知限制

- 只在 Windows x64 上构建并验证过；需要 `PATH` 上有 Git。
- **自动更新只对 NSIS 安装版生效。** portable 每次解压到临时目录，没有可替换的安装根，只能跳下载页。
- 每次发版必须把 `latest.yml` 与 `*-setup.exe.blockmap` 一起传到 Release，否则更新器根本看不到有版本可更。
- 安装包**未做代码签名**，首次运行会有 SmartScreen 提示。
- CLI 不提供模型目录接口，模型名仍需手填；填错时服务商返回的名字会被做成可点按钮（已配置的服务仍要靠一次失败测试才知道可用模型名）。上游提议：[alibaba/open-code-review#1694](https://github.com/alibaba/open-code-review/issues/1694)。
- 开发实例与安装版共用同一份用户数据，**单实例锁会让后启动的窗口静默退出**。
